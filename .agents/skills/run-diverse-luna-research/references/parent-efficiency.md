# Parent efficiency for sustained work

Use this procedure when a large-context parent is repeatedly collecting information, executing tools, checking children, or resuming a goal. Preserve its selected model, required quality, full objective, and supported goal continuation. This procedure supplements the workflow; it does not replace access rules, acceptance checks, or the global N/C/W/V ledger.

## Delegate complete units

1. Identify the next acceptance condition and the few decisions the parent must make. For research, lease non-overlapping source/claim cells; for delivery, assign a complete build/fix/verification unit to its owner. Give the child the current object/revision, required evidence, ownership, dependencies, and stopping boundary. Do not copy the full conversation.
2. Let the child choose and run its bounded sequence of searches, implementation, and relevant checks. Do not turn each command into a new parent follow-up. The parent must not redo the same collection or execution while that owner is working. Independent review remains independent.
   If the parent has spent roughly 20 model steps on one acceptance unit, or repeatedly carries more than about 150,000 input tokens while collecting/executing, review its ownership before the next repeated operation. Move separable collection and execution into an autonomous child packet, batch local checks, or change the failed method. These are review triggers, not task-completion limits; root-only authority and necessary decisive judgment remain at the parent.
3. Preserve the explicit Luna/low fresh-context route and verify the first useful completed child. Start with W=1-2 and at most W=3, with C<=6 and the same objective-wide N (default 6, maximum 12). Before an additional assignment, name its remaining acceptance condition, why the existing owner cannot handle it, its disjoint scope and remaining credits. Followup calls and failed starts count; default to flat leaves.

## Keep the parent input compact

Return the observed result, decisive evidence locations, revision/diff, relevant check results, remaining gaps, and required parent decision. A concise summary normally fits about 1,000-2,000 tokens; retain larger necessary evidence in artifacts and cite its exact location. This is an input-efficiency target, not a quality or output truncation gate.

Use the existing checker to reconcile parent/child UUIDs and exact completed-turn receipts in a batch. Read its concise result and resolve reported exceptions; do not paste whole rollouts into the parent. Root still verifies every accepted result and conclusion-grade source under the workflow's freshness and source-family rules. Reuse an already verified unchanged source snapshot rather than downloading and rereading it for every child or continuation.

## Continue from the same frontier

At a meaningful acceptance boundary, keep the full objective, verified revision, accepted result IDs, active owners, remaining conditions, and the next operation in the existing ledger/checkpoint. A goal wakeup resumes that frontier and the same N/C/W/V accounting. It does not create a new budget, dispatch replacement owners for active work, repeat completed checks, or start an extra independent review because time passed.

If work is pending, use the native child/process wait for a bounded interval supported by the current runtime; report meaningful changes, not every poll. Unchanged input with no acceptance progress calls for a different method or a precisely evidenced blocker. Necessary finite processing and authorized fixes still continue through completion or verified failure. A child packet is not final acceptance of the user's whole objective.

## Verify economy without inventing billing

Review parent model-call count and context growth at the accepted milestone, alongside total parent/child attempts and any available quota readback. Compare a matched work unit with the earlier parent-heavy pattern. Avoid repeated account polling and do not equate cached cumulative input with unique text, dollars, or exact subscription consumption. Record reduced spending only after observation; keep completion and required evidence as separate acceptance criteria.

## Dispatch limits and trace preflight

The local operating policy starts with W=1-2, permits at most W=3 starts per wave,
and caps all open children (including coordinators) at C=6. Choose one objective-wide
N=6 by default, never more than N=12; failed spawns, probes, retries, verifiers and
every followup_task invocation consume that same N. Keep V=max(1,ceil(.15*N)).
Use flat leaves by default. A coordinator needs an explicit root grant and spends
the same credits; another level or a goal wakeup does not mint credits.

Before the first dispatch, initialize one state at work/delegation-budget-OBJECTIVE.json with
scripts/check_dispatch_budget.py --state work/delegation-budget-OBJECTIVE.json --init
--root-rollout /absolute/current-root.jsonl --budget 6. Use an actual root trace,
not a child or a fabricated receipt. Before each batch of spawn/followup calls,
rerun it with --new-spawns K --new-followups L and the open-child count obtained
from list_agents via --open-children J. Register each observed child trace through
--add-rollout /absolute/child.jsonl before allowing it to delegate. The preflight
counts actual native calls, including unsuccessful attempts; registering a child
does not replace the independent runtime/provenance checks. --verification may
spend the protected reserve only on required verification.

Retain the same state, start time, registered tree and greatest observed count over
goal continuation, corrections and followups. Reinitialization is rejected. Larger
budgets require a root-recorded remaining acceptance condition and a different
bounded hypothesis at the start; the checker still rejects N>12, C>6 and W>3.
After the limit, required implementation, tests and fixes continue at the parent;
only new child dispatch stops. A new user objective may have a new state, while a
new wave, coordinator, retry or automatic continuation of the same objective may not.
This preflight is a skill gate, not a hook intercepting every native tool call.
The configured C limit is the runtime control; actual savings require observation.
